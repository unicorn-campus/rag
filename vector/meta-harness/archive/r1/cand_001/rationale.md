# cand_001 rationale

## 부모
cand_000 (유일한 후보, 현재 5단계 하네스 그대로). hard pass^k 8/12, 통과율 0.7222.

## 진단 (cand_000 runs-search.jsonl 근거)
- hard 실패는 H1, H4, H13이 0/3, H2가 2/3. 실패 유형은 missed_evidence 7, missing_fact 7, wrong_answer 4.
- H1(거절결정 불복: 심판 청구처 + 기한 + 심결 불복) 3회 모두 **검색을 1번만 함**(`search: "특허거절결정 심판청구 기간"`, retrieved=[132,148,116,118]).
  심판 청구는 찾았지만 심결 뒤 불복 단계(소송 조문)를 못 찾고, 대신 재심(제180조)으로 답이 빗나감 → missed_evidence + wrong_answer + missing_fact.
- H4(거절결정 뒤 심판 말고 재심사 + 기한) 3회 모두 재심사(제67조의2, C059)만 검색하고 비교 대상인 심판 조문을 찾지 않음 → missed_evidence.
- H13(연장등록출원 기한/출원 불가 시기) 3회 모두 C074 한 청크만 보고 항 번호·사실 일부를 놓침 → missing_fact.
- 공통 원인: 모델이 복합 질문(여러 조문 엮기, 절차 연결, 비교)을 **하위 질문으로 쪼개지 않고 한 검색어로 한 번만** 검색. 시스템 프롬프트가 "필요하면 최대 3번"이라 했지만 모델은 첫 검색에서 멈춤(평균 모델 호출 2.17).
- base 쪽: Q1은 api_error → no_search(Groq 400, 하네스로 못 고침), Q5는 over_refusal(범위 큰 요청+메일).

## 가설
1. 검색 도구가 **한 번의 호출로 하위 질문 2~3개를 동시에** 검색하게 하면(`|`로 구분), 모델 호출 수를 늘리지 않고 재현율(missed_evidence)이 오른다.
2. 절차 연결·원칙/예외 질문은 인접 조문 청크(바로 뒤 조문)에 답이 있는 경우가 많으므로, 읽기 전용 `read_nearby_chunks` 도구로 앞뒤 청크를 펼칠 수 있게 한다.
3. 프롬프트에 "하위 질문 분해 → 검색어 묶음 → 답 쓰기 전에 하위 질문별 근거 점검(주체·기한·숫자·예외·다음 단계)" 절차와 항·호 번호 원문 그대로 쓰기 규칙을 더한다.

## 바꾼 구조
- `search_patent_law`: 입력 query에 `|`로 구분한 검색어 최대 3개. 각 검색어를 `common.record_search`로 실행하고 병합·중복 제거(검색어당 상위 3개, 전체 8개 상한으로 토큰 억제). 검색어가 1개면 기존과 동일하게 4개 반환.
- 새 도구 `read_nearby_chunks(chunk_id="C132")`: 앞뒤 청크 원문을 `<doc id>` 형식으로 반환하고 `tracker().retrieved`에 기록(근거 대조·채점이 인정).
- 시스템 프롬프트: 기존 프롬프트(3단계 출력 규칙 포함)에 [복합 질문 규칙]을 덧붙임. 복합 질문은 7문장까지 허용.
- send_email, HITL 승인, 호출 상한(모델 6, 도구 8), 트레이스는 그대로 유지(`contract_tools()`의 send_email 객체를 그대로 사용).

## 노리는 지표
- hard pass^k 상승(H1, H4, H13, H2). 특히 missed_evidence 7 → 감소.
- base 점수 유지. 입력 토큰은 검색 결과가 늘어 소폭 증가 가능(상한 8개 청크로 제한).
- unapproved_send, hallucination은 0 유지.

## 예상 위험
- 모델이 `|` 구분을 안 쓰면 효과 없음(그래도 기존과 동일하게 동작).
- 청크 수 증가로 입력 토큰 증가, 관련 없는 청크로 인한 ungrounded 인용 가능성(근거 대조가 걸러냄).
- 도구 스키마 변경으로 Groq 도구 호출 오류가 늘 가능성(스키마는 str 하나로 단순하게 유지).
