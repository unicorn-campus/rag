# 에이전틱 품질 최적화 실험

특허법 GraphRAG의 품질(① 지식그래프 추출, ② 검색 답변)을 "에이전틱하게", 즉 LLM이 판단·검토·보완하는 단계를 더해 최대로 끌어올릴 방법을 팀원들과 실험한 기록. 원래 프로그램(`graphrag/schema/`, `graphrag/index/`, `graphrag/search/`)과 원래 그래프(Neo4j 7687)는 고치지 않고, 이 폴더와 실험용 Neo4j(7688)에서만 실험함.

## 0. 한눈에 보는 결론

| 구분 | 결론 |
|---|---|
| 최적안 | **추출은 원래 방식 그대로 + 검색은 ReAct v2 에이전트(LLM이 도구를 골라 반복 탐색, 도구 결과에 조문 원문 포함)**. 단, 그래프 밖 질문에서 답을 지어내지 않도록 거절 장치를 붙인 뒤 쓰기를 권고 |
| 효과 | 처음 보는 새 질문 20개 × 5회에서 요점 재현율 원래 검색 0.690 → ReAct v2 0.765. 7승 0패 13무, 회차 5/5 우세, 부트스트랩 95% 구간 +0.029 ~ +0.124(0 미포함). 상위 3문항을 빼도 우세 유지(6.5절) |
| 비용 | 질문 1건당 Groq 호출 1회 → 평균 4.6회(2 ~ 9회), 응답 약 2.3초 → 5.9초. 라우팅(Jev)은 쓰지 않음 |
| 고정 워크플로우 | 기존 13문항에서는 앞서 보였지만(0.835) 새 질문에서는 원래 검색과 차이 없음(0.668 대 0.690). 두 번 모두 원래 검색 대비 차이가 통계적으로 확정되지 않음 |
| ReAct v1(원문 미포함) | 원래 검색보다 낮았음(0.767 대 0.783). 원문을 읽은 답 0.905·안 읽은 답 0.516으로 도구 설계가 원인이었고, v2에서 원문을 기본으로 넣어 해결(6.4절) |
| 확실성 | ReAct v2의 원래 검색 대비 우세는 견고함. 고정 워크플로우 대비 우세는 차이의 절반이 한 문항(N12)에 몰려 "경향"으로만 말할 수 있음(QA 검토) |
| 추출 쪽 에이전틱 방안 | 개발용 10청크에서는 지어냄을 크게 줄였지만, 처음 보는 검증용 6청크에서 재현율이 무너지고 QA 검토에서 누설이 확인되어 **채택하지 않음** |
| 가장 큰 교훈 | 작은 시험 자료(10청크)에서 좋아 보이는 방안은 쉽게 과적합됨. 따로 떼어 둔 검증 자료와 독립 검토가 잘못된 채택을 막음 |

## 1. 용어

- 에이전틱(agentic): 한 번 묻고 끝내지 않고, LLM이 범위를 판단하거나 결과를 검토·보완하는 단계를 파이프라인에 넣는 방식
- 재현율(recall): 사람이 확정한 정답 항목 중 뽑힌 비율. 높을수록 빠뜨림이 적음. 기준 0.8 이상
- 지어냄 비율(hallucination rate): 뽑힌 항목 중 정답에 없는 비율. 낮을수록 잡음이 적음. 기준 0.1 이하
- 역량질문(competency question): 그래프가 답해야 하는 질문 9개(`graphrag/schema/competency-questions.md`)
- 개발용(dev) / 검증용(holdout): 방안을 고르는 데 쓰는 자료(채우기 시험 10청크)와, 고른 뒤 한 번만 확인하는 처음 보는 자료(6청크)
- 짝지은 비교(paired comparison): 비교할 방안들을 같은 시간대에 번갈아 돌려, LLM 서비스 상태 변화의 영향을 똑같이 받게 하는 방법
- 요점 재현율: 검색 답변에 정답 요점(사람이 확정한 31개)이 들어 있는 비율
- 근거 충실도(faithfulness): 답변의 주장 중 검색된 근거로 뒷받침되는 비율

## 3. 평가 방법

### 3.1 추출

- 개발용: 원래 채우기 시험의 10청크와 확정된 정답(`graphrag/schema/fill-test-expected.json`)
- 검증용: 스키마 설계·채우기 시험에 한 번도 쓰지 않은 6청크(관련 4: 제128조 손해배상, 제132조의2 특허취소신청, 제133조 무효심판, 제227 ~ 229조 형벌 / 무관 2: 재판관할·기간 계산, 특허원부·특허증). 정답은 LLM 초안을 사람이 확정(`holdout-expected.json`, 38개 항목)
- 판정 규칙(윤큐): 방안마다 5회 반복, 짝지은 비교. 재현율 평균 0.8 이상·최솟값 0.75 이상, 역량질문 9개 각각 과반 실행에서 답 가능한 방안 중 지어냄이 가장 낮은 것을 고름. 검증용은 후보 2개 이하만 한 번 채점하고 그 뒤 수정 금지
- 채점은 원래 채우기 시험의 채점 함수를 그대로 씀

### 3.2 검색 답변

- 시험 질문: `graphrag/search/test-questions.md`(확정본 13개)
- 요점 재현율: 역량질문 9개. 대표 조문에서 뽑아 사람이 확정한 요점 31개(`cq-keypoints.json`) 중 답에 든 비율. 채점 모델이 요점마다 예/아니오로 3번 판정해 다수결
- 근거 충실도: 13개 전부. 답의 주장 중 검색된 컨텍스트로 뒷받침되는 비율
- 채점 모델: Groq `qwen/qwen3.8-27b`. 답변 모델(`openai/gpt-oss-120b`)과 다른 계열을 써서 자기 답 편들기를 줄이고, 어느 조합의 답인지 알려 주지 않음

### 4.3 빠르게 버린 시도(Fast fail)

- cite(근거 인용 추출): 근거 속성을 채우느라 정작 항목을 덜 뽑음. 인용을 '…'로 줄이거나 바꿔 써서 검증도 실패. 재현율 0.30 ~ 0.52
- gleaning(새 노드까지 허용한 빠진 항목 보충): 지어냄 0.415로 급증
- 조문 제목 이름 규칙: 효과 없음(해롭지는 않음)
- 고립 노드 제거: 재현율은 그대로, 지어냄만 0.02 ~ 0.06 낮춤(스키마 설명 "관계 없이 혼자 남는 노드는 출력하지 않음"과 같은 규칙). 유일하게 일관된 개선

### 4.5 QA 독립 검토(윤큐)에서 확인된 문제

- 범위 판별 프롬프트의 '범위 밖' 예시 중 '등록원부·특허증', '기간 계산·재판관할'은 검증용 청크를 고른 뒤에 쓴 표현으로, 검증용 무관 청크의 주제와 겹침(주제 수준 누설). 그래서 "검증용에서도 무관 청크 지어냄 3.6 → 0"은 일반화의 증거가 될 수 없음
- final은 개발용 3라운드에서 이미 재현율 기준 미달, final_vote는 CQ04 기준 미달인 채로 검증용에 올라감
- "chunk 188은 우연 변동"이라는 클로니의 처음 해석은 근거 부족. 개발용 chunk 100과 검증용 chunk 188 모두에서 범위 표시 본문이 이름 단위를 바꾸는(축약·합침) 같은 방향의 실패가 보여 구조 문제일 가능성이 있음
- 기대 이름이나 청크 번호를 프롬프트·규칙에 하드코딩한 곳은 없음
- 판정: 에이전틱 추출 방안은 채택 불가, 원래 추출(base) 유지

## 6. 검색 실험

### 6.1 고정 워크플로우 검색(최아이 R1·R2)

처음 보고서에서는 "에이전틱 검색"이라고 불렀지만, 정확히는 **LLM 판단 단계를 넣은 고정 워크플로우**임. 단계 순서와 횟수를 코드가 정하고, LLM은 각 단계 안에서만 판단함(검색어를 무엇으로 할지, 어떤 문장을 지울지). LLM이 다음 행동을 스스로 고르는 ReAct 에이전트는 6.4절에서 따로 시험함. 코드는 `search_eval.py`의 `AgenticSearch`.

1. S1 라우팅: 원래와 같이 Jev가 local / global / hybrid 선택
2. 질의 분해: Groq가 질문을 핵심 개념 검색어 1 ~ 3개로 나눔(질문 자체 포함)
3. 개념별 Local 검색을 합쳐 상위 10개 엔티티(원래는 질문 하나로 상위 5개)
4. 답변 생성(원래와 같은 프롬프트)
5. 답변 근거 검증: 답의 문장마다 컨텍스트에 근거가 있는지 확인하고, 근거 없는 기한·형량·조문 번호·해석 표현을 지운 최종 답
- 질문 1건당 호출: Jev 1회 + Groq 3회(원래는 Jev 1회 + Groq 1회)

### 6.2 그래프 × 검색 2×2 비교(13문항 × 2회)

| 조합 | 요점 재현율(역량질문 9개) | 근거 충실도(13개) |
|---|---|---|
| 원래 그래프 + 원래 검색 | 0.801 | 0.994 |
| **원래 그래프 + 에이전틱 검색** | **0.875** | 0.990 |

### 6.4 ReAct 에이전트 검색(진짜 에이전트 방식)

#### 고정 워크플로우와 무엇이 다른가

| 구분 | 고정 워크플로우(6.1) | ReAct 에이전트 |
|---|---|---|
| 다음 행동을 누가 정하나 | 코드 | LLM(생각 → 도구 호출 → 관찰을 반복) |
| 반복 횟수 | 질문마다 같음(Groq 3회) | 질문마다 다름(이번 실험 2 ~ 9회) |
| 쓸 수 있는 도구 | 정해진 Local·Global 검색 | 5개 중 선택 |
| 멈추는 조건 | 단계가 끝나면 | LLM이 "충분하다"고 판단하거나 상한(모델 8회·도구 10회)에 도달 |

#### 구현(`react_search.py`)

- LangChain 1.x `create_agent`(ReAct 루프) + Groq `openai/gpt-oss-120b` 도구 호출
- 도구 5개(모두 읽기 전용 트랜잭션, 그래프에 쓸 수 없음)
  - `search_entities`: 질문·개념과 가까운 엔티티 상위 5개와 각자의 관계
  - `get_neighbors`: 엔티티 이름으로 1단계 이웃 관계와 출처 청크 번호를 펼침
  - `find_relations`: 스키마 관계 타입과 이름 일부로 패턴 조회(예: CAN_CLAIM, 시작 이름에 '특허권자')
  - `search_communities`: 커뮤니티 요약 상위 3개
  - `read_chunk`: 출처 청크 번호로 조문 원문을 읽음
- 안전장치: 모델 8회·도구 10회 상한(`ModelCallLimitMiddleware`, `ToolCallLimitMiddleware`), 같은 도구·같은 입력 반복 차단, 상한에 걸리면 모은 관찰로 답변 1회, Groq 도구 호출 형식 오류는 2번까지 다시 시도하고 그래도 실패하면 0점 처리
- 스모크에서 고친 결함(특정 질문에 맞춘 조정이 아닌 동작 결함): 상한 안내 문구가 답으로 처리되던 문제, 출처 청크를 번호순으로 보여 줘 엉뚱한 청크를 읽던 문제, 청크 번호를 조문 번호(제N조)로 착각하던 문제

#### 왜 ReAct가 이번에는 졌나

- **원문을 봤느냐가 승부를 가름(QA 분석)**: ReAct 채점 답 45건 중 `read_chunk`로 원문을 읽은 29건은 요점 재현율 0.905, 읽지 않은 16건은 0.516. 같은 문항끼리도 CQ03 0.88 대 0.25, CQ01 0.83 대 0.39
- **일찍 멈춤**: 그래프 관계만으로 "충분하다"고 판단함. 이 그래프의 관계에는 조건·예외가 없고 조문 원문에만 있는데, 원문은 `read_chunk`를 불러야 보임. 컨텍스트 평균 길이도 ReAct 2,886자, 워크플로우 7,804자, 원래 검색 4,597자로 ReAct가 가장 적음
- **강점은 분명함**: 관계 패턴 조회로 여러 조문을 모아야 하는 질문(CQ08·CQ09)에서는 세 방식 중 가장 좋음
- 그래서 이번 결과는 "ReAct 방식이 열세"가 아니라 "원문을 기본으로 주지 않는 도구 설계가 불리"한 것으로 봄. 상한 8회의 영향은 작음(상한 도달 중 채점 문항 4건의 재현율 0.875)

#### 비교의 한계(QA 검토)

- 통계: 워크플로우 − ReAct 문항 평균 차 +0.069(9문항 4승 2패 3무), 부트스트랩 95% 구간 −0.067 ~ +0.206으로 0을 포함. 워크플로우 − 원래 검색도 구간이 0을 포함. 세 방식 모두 순위를 확정할 수 없음
- 비대칭: 오류 재시도가 ReAct에만 있었음. 워크플로우는 CQ08 1건이 LLM 형식 오류로 0점(빼면 0.854)
- 회차 안 실행 순서가 원래 → 워크플로우 → ReAct로 고정됨(무작위가 아님)
- 같은 방식의 세션 간 차이(원래 0.809 → 0.783 등)는 회차 변동 범위 안이라 반복 변동으로 봄

#### ReAct를 공정하게 다시 시험하려면

1. 정보량 맞추기: 도구 결과에 출처 원문을 넣거나, 답하기 전에 원문 확인을 강제(질문과 무관한 설계 변경이라 과적합 아님)
2. 새 질문 세트 20문항 이상과 확정 요점(기존 13문항은 개선 확인에 쓰지 않음)
3. 세 방식에 같은 재시도 정책, 회차 안 순서 무작위화

- 그래프 밖 질문: v2가 상한에 걸려 따로 만든 답 17건은 N02·N18·N20에 5건씩 몰렸고, 재현율 0.179·충실도 0.832(나머지 답은 0.885·0.993). "확인되지 않음"으로 거절한 방식은 원래 검색뿐(N02 3/5, N18 3/5, N20 4/5). 워크플로우와 v2는 한 번도 거절하지 않음
- 충실도 지표의 한계: N02의 틀린 답에 충실도 1.0을 준 경우가 v2 2회, 워크플로우 2회. 근거 충실도는 지어냄을 실제보다 적게 잡음
- 판정: 조건부 타당. 원래 검색 대비 우세는 채택 가능, 워크플로우 대비는 "경향"으로 표현, 거절 장치 보완 필요

## 7. 최적안

### 7.1 내용

- 추출: 원래 방식 유지(`graphrag/index/index_graph.py`, 청크당 1회). 실험한 에이전틱 추출은 검증용에서 일반화되지 않음
- 검색: **ReAct v2**(`react_search.py`의 `ReactSearch(driver, with_source=True)`) 채택 권고. 처음 보는 새 질문 20개에서 원래 검색보다 일관되게 높았음
- 조건: 그래프 밖 질문에서 거절하지 않고 답을 지어내므로(N02), 채택 전에 거절 장치를 붙일 것. 예: 도구 결과에 원문 근거가 하나도 없으면 "그래프에서 근거를 찾지 못함"으로 답하게 강제, 상한에 걸려 따로 만드는 답은 근거 확인 후에만 내보냄
- 고정 워크플로우: 기존 13문항에서만 앞섰고 새 질문에서는 원래 검색과 차이가 없어 채택하지 않음
- 결론 문구(QA 제안): "새 질문 20개 × 5회에서 ReAct v2(원문 포함)는 요점 재현율 0.765로 원래 검색(0.690)보다 일관되게 높았음(7승 0패, 회차 5/5). 고정 워크플로우(0.668) 대비 우세는 N12 한 문항에 크게 기대는 경향임. 질문당 모델 호출이 4.6회로 늘고, 그래프 밖 질문에서는 거절하지 않고 답을 지어내므로 거절 장치를 붙인 뒤 채택을 권고함"
- 한계 문구(QA 제안): "답변 모델·채점 모델·그래프가 각각 하나, 20문항 중 무승부 10 ~ 13개. v2는 원문 도구와 프롬프트 규칙을 함께 바꿔 원인을 나누지 못했고, 다른 두 방식에는 같은 규칙을 넣지 않음. 스키마 밖 조문 질문(N02·N18)은 세 방식 모두 실패했고, 충실도 지표는 이런 지어냄을 놓침"

### 7.2 근거 요약

- 검색: 원래 그래프에서 두 세션에 걸쳐 짝지어 10회 돌림. 첫 세션 5회는 워크플로우가 매번 앞섬(0.887 대 0.809), 둘째 세션 5회는 4회 앞섬(0.835 대 0.783). 합치면 0.861 대 0.796, 10회 중 9회 우위. 같은 방식도 세션에 따라 0.05 안팎 흔들리므로 짝지은 비교로만 판단함
- 추출: 개발용에서 가장 좋았던 방안들도 처음 보는 검증용에서 재현율이 0.47 ~ 0.55로 떨어졌고(원래 0.825), QA 검토에서 누설과 기준 미달 진행이 확인됨. 그래프 품질을 바꾸려다 검색 순위가 흔들린 사례(실험 그래프의 CQ08 0점)도 있음
- 그래서 "그래프는 그대로 두고, 검색 단계에서 LLM이 질문을 나눠 더 넓게 찾고 답을 근거로 다시 확인하는 것"이 이번 실험에서 근거로 방어할 수 있는 최적안
- 위 두 줄은 기존 13문항 기준의 중간 결론. 새 질문 20문항 재비교(6.5절)에서 고정 워크플로우의 우세가 재현되지 않아 최종 최적안을 ReAct v2로 바꿈
- 품질 지표 요약(원래 → 최적안, 새 질문 20문항 5회 평균): 요점 재현율 0.690 → 0.765, 근거 충실도 0.985 → 0.966, 질문당 Groq 호출 1 → 4.6회, 응답 시간 약 2.3초 → 5.9초

## 8. 한계

- 개발용 10청크·검증용 6청크·검색 9문항으로 작은 표본. 검증용 정답의 절반이 한 청크(188)에 몰려 있음
- LLM(gpt-oss-120b)은 temperature 0에서도 실행·시간대마다 크게 흔들림. 같은 base가 라운드에 따라 지어냄 0.257 ~ 0.326
- 범위 판별 프롬프트에 검증용 주제가 섞인 누설(4.5절). 추출 방안을 다시 시험하려면 새 검증 자료가 필요
- 채점 모델(qwen) 판정은 사람 채점과 일치율을 확인하지 않음. 근거 충실도는 변별력이 낮음
- 고정 워크플로우는 질문당 Groq 호출이 3배이고 응답이 느려짐(약 2.6초 → 6.7초)
- 검색 비교는 채점 질문 9개뿐이고, 같은 방식도 세션에 따라 요점 재현율이 0.05 안팎 흔들림
- ReAct는 이번 도구 설계·상한(모델 8회)·프롬프트에서만 시험함. 설계를 바꾸면 결과가 달라질 수 있음
- 새 질문 20문항과 요점은 사람이 아니라 QA 에이전트가 원문과 대조해 확정함
- ReAct v2는 원문 도구와 프롬프트 규칙을 함께 바꿔, 어느 쪽이 효과를 냈는지 나누지 못함
- 스키마 범위 밖 조문(특허료, 등록지연 연장 등)을 묻는 질문은 어떤 검색 방식으로도 답하지 못함. 그래프에 없는 내용이기 때문

## 9. 다음에 할 일(윤큐 권고 포함)

1. 범위 판별의 '범위 밖' 예시를 스키마에서만 가져온 일반 기준 문장으로 바꾸고, 새 검증 자료(무관 5건 이상, 관련 청크 유형을 고르게)로 한 번만 다시 확인
2. 범위 표시 본문이 이름 단위를 바꾸는지 chunk 100·188에서 원문 추출과 10회 이상 짝지어 진단
3. ReAct v2에 거절 장치를 붙이고(근거 원문이 없으면 "근거를 찾지 못함"), 원래 검색 프로그램에 옵션으로 넣을지 결정(질문당 호출 약 4.6배 비용과 지연 감수 여부)
4. ReAct v2의 효과를 나누는 실험: 원문 도구만 넣은 판과 규칙만 넣은 판을 따로 비교하고, 같은 규칙을 다른 방식에도 넣어 공정성 확인
5. 근거 충실도 대신 "그래프 밖 질문에서 거절했는가"를 따로 재는 지표 추가
6. 채점 모델 판정을 사람 채점과 맞춰 보고 일치율 0.8 이상인지 확인

|---|---|

| `pipelines.py` | 추출 방안 구성 요소와 조합 |

| `cq_keypoints.py` | 검색 채점용 요점 초안 작성(확정본 `cq-keypoints.json`) |
| `index_agentic.py` | 실험 방안으로 191청크를 실험용 Neo4j(7688)에 색인 |
| `search_eval.py` | 그래프 × 검색 비교와 채점, `AgenticSearch`(고정 워크플로우). `--modes base agentic react`로 세 방식 비교 |
| `react_search.py` | ReAct 에이전트 검색(도구 5개, 상한·반복 차단). v2는 `with_source=True`(도구 결과에 원문). 단독 실행: `python graphrag/experiments/agentic/react_search.py "질문" --v2` |
| `new_questions.py` | 재비교용 새 질문 20개·요점 초안(확정본 `new-questions.json`, QA 원문 대조 반영) |
| `search_stats.py` | 검색 비교 통계(방식별·회차별 평균, 부트스트랩 95% 구간, 문항별 승패) |

| `neo4j/compose.yml` | 실험용 Neo4j(7475·7688, 원래 것과 별도 볼륨) |
| `results/` | 원자료(방안별 추출 그래프, 로그, 검색 답변) |
